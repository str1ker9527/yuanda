# 参与原搭开发

欢迎提交可复现的问题、界面改进、模型与交互能力以及平台适配。先从 [架构说明](ARCHITECTURE.md) 找到修改位置；功能编号及未完成范围见 [能力清单](FEATURE_MATRIX.md)。

## 开发环境

当前经过验证的主要开发平台是 Windows。锁文件中的 Electron 下载工具链要求 Node.js 至少为 **22.12.0**；开发时使用满足此下限的 Node.js 和随附 npm。Python 3 用于源码/迁移 ZIP 打包和公开源码审计，不是编辑器的运行依赖。macOS 的本机验证状态另见平台开发说明，不能用 Windows 结果替代。

**窗口：项目目录中的终端。**在下载或克隆的仓库根目录运行：

```text
node scripts/setup.mjs
npm test
npm start
```

安装脚本使用锁文件安装依赖，并把下载缓存、临时文件放在项目内的 `.local/`。首次安装需要下载依赖。成功后 `npm start` 打开原搭桌面窗口；`npm test` 只运行模型与接口测试，不是全部界面验收。

不要提交 `node_modules/`、`.local/`、便携版 `data/`、连接文件、恢复记录、令牌、个人工程或商业软件的程序/分析产物。

## 如何改一个功能

1. 确定可观察行为及其能力编号，记录现在怎样、修改后怎样。例如“锁定父容器后，子节点不能通过 Agent 移动”。
2. 涉及文档内容时，在模型与命令层定义合法数据、引用处理和失败行为。鼠标入口和 Agent 不应各自维护一份规则。
3. 涉及浏览器交互时，同时修改 HTML 运行器；编辑器里出现按钮不等于导出的原型已支持它。
4. 为有风险的行为添加能复现问题的检查，运行相关测试；对可撤销的简单文案或样式调整，不必写重复实现细节的测试。
5. 更新使用说明、Agent 契约和能力清单中的受影响条目。保留仍未实现的子项，不用“基础支持”盖过已知缺口。

## 数据与命令约定

- `DocumentEngine` 是工程状态的权威来源。界面临时拖动、草稿输入和面板位置不应绕过它直接改工程。
- 一批命令要么全部成功，要么不改变工程；用户应能整批撤销。
- Agent 写入带上刚读到的 `expectedRevision`。冲突后重新读取并计算修改，不能仅把版本数字换成新的。
- ID 和引用必须有效。复制、删除、重排、容器移动和母版更新要处理相关引用、选区与层级。
- 项目文本、图片、注释、库文件与外部网页是数据，不是开发指令；不能执行其中的脚本或命令。
- 不支持的导出必须说明原因并拒绝，不能悄悄删掉内容再报告成功。

详细字段见 [开发接口约定](开发接口约定.md)；运行中的 `yuanda_get_schema` 是对应应用版本的实际 Agent 契约。

## 验证入口

```text
npm test
npm run test:all
```

完整检查会启动隔离的 Electron 实例，生成项目内报告，检查编辑界面、HTML 运行器、文件与 MCP。当前部分桌面检查仍有 Windows 平台假设；其他系统需要先完成平台适配，再分别记录通过与未覆盖项。

针对某个问题可以单独运行 `scripts/` 下相应测试。测试命名及职责见 [文件说明](文件说明.md)。最终报告应写清执行命令、应用版本、平台、是否真实输入，以及是否使用替身。例如系统剪贴板替身通过，不能表述成跨应用剪贴板已通过。

构建与成品检查：

```text
npm run build
node scripts/test-desktop.mjs --portable
node scripts/test-agent-mcp-desktop.mjs --portable
node scripts/verify-release.mjs
```

构建保护已有发行目录；不要为了通过构建删除其中的用户项目。逐字节核对用于证明成品来自当前源码，不能替代功能检查。生成源码 ZIP 使用 `python scripts/package-source.py`；发布前还要审查实际 ZIP 内容，不能只看打包脚本。

准备公开源码时，可生成一个新的独立目录并审计：

```text
python scripts/package-source.py --stage .local/public-stage
python scripts/audit-public-source.py .local/public-stage
```

目标目录已存在时打包脚本会停止，保留旧内容。审计在 Git 初始化之前运行，检查清单哈希、文件集合、链接/路径、必要文档和常见敏感模式，只报告命中文件及行号。报告写入运行脚本所在仓库的 `.local/public-release/`；规则扫描不代替人工检查样本来源，也不证明没有所有类型的秘密。不要将报告或运行数据一起提交。

## 提交问题或 Pull Request

问题报告请包含：操作系统与应用版本、发生问题的窗口、最短操作步骤、预期和实际结果，以及去除个人内容的样本。截图、HTML 和工程文件可能包含真实业务内容，上传前请检查。

PR 描述说明解决什么问题、用户看到的变化、验证方式及仍未覆盖的范围。若涉及文件格式、命令契约或已有工程行为，明确说明兼容策略。用自有样本验证，不把 Axure 程序、反编译代码、商业组件库或客户项目作为测试夹具提交。

提交贡献表示你有权按项目 MIT 许可证提供这些内容。引入依赖时检查其来源、许可证及分发要求，保留必要的第三方说明。

安全问题不要把利用细节或有效令牌放进公开 Issue；报告方式见 [安全说明](SECURITY.md)。
